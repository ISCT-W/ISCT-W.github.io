LLM推論：KV Cache・連続バッチ処理・配信性能

推論の最適化は生成速度一つでは測れません。

W韋 君豪読了目安 5 分

推論の最適化は生成速度一つでは測れません。長い入力のPrefill、逐次生成時のキャッシュ参照、複数リクエストでデバイスを共有するスケジューリングが、遅延、処理量、メモリを左右します。費用の発生箇所を分けてから、キャッシュ、量子化、バッチ、並列化がどのボトルネックを解くか判断します。

図の構造を見る（原文）
flowchart LR
    Q["等待队列"] --> S["调度器"]
    S --> P["Prefill：处理输入并建立 KV"]
    P --> K["活动请求的 KV 缓存"]
    S --> D["Decode：计算新 token"]
    K --> D
    D --> K
    D --> C{"请求是否结束"}
    C -->|"否"| S
    C -->|"是"| R["回收 KV 块与调度槽位"]
    R --> S

連続バッチ処理は固定した一組の完了を待たず、生成反復の間で実行中のリクエストを入れ替えます。ただしPrefillとDecodeは資源を競合するため、スループットが増えても初回出力や裾の遅延が下がるとは限りません。

KV Cacheが除くのは過去の再計算

トークン ttt の生成時、過去 t−1t-1t−1 トークンの各層のKeyとValueは変わりません。これらを保存し、新しいトークンのQ/K/Vだけを計算して、蓄積したKey/Valueを参照します。接頭辞全体の再実行を避けられます。

計算量とメモリ

キャッシュがなければ、毎回長くなる全系列を再計算します。キャッシュ後は過去の射影や前段の計算を繰り返しません。ただし新Queryは ttt 個のKeyと計算するため、一段階のAttentionは約 O(t)O(t)O(t)、生成全体は約 O(T2)O(T^2)O(T2) です。過去の順伝播を省くのであって、すべてのAttentionを厳密に線形にするわけではありません。

KVメモリの概算は次です。

MKV=2×L×T×Hkv×dhead×b×BM_{KV}=2\times L\times T\times H_{kv}\times d_{head}\times b\times BMKV​=2×L×T×Hkv​×dhead​×b×B

2はK/V、LLL は層数、TTT は保存長、HkvH_{kv}Hkv​ はKVヘッド数、bbb は要素のバイト数、BBB は同時系列数です。

最適化の方法

  • MQA/GQA： 複数のQueryヘッドで少数のKVヘッドを共有する。
  • KV量子化： FP8/INT8などで保存精度を下げる。
  • Paged KV Cache： ページ単位で確保し、予約領域の無駄や断片化を減らす。
  • Sliding Window/Chunked Attention： 参照する履歴を限定する。
  • Prefix Cache： 同一のプロンプト接頭辞をリクエスト間で再利用する。
  • KV Offload： CPUなどへ移し、転送費用と引き換えに容量を空ける。

遅延・処理量・費用を合わせて見る

遅延、スループット、同時実行、メモリ、単価を測り、PrefillとDecodeを区別します。tokens/sだけでなく、単一リクエストかデバイス全体か、入出力長、バッチ、分位点を示す必要があります。

主な指標

指標 意味 主な要因
TTFT 到着から最初の出力トークンまで 待ち行列、入力長、Prefill、スケジューリング
TPOT / ITL 出力トークン間の平均時間 Decode、KV帯域、バッチ、通信
E2E遅延 回答全体の所要時間 TTFT＋出力長×TPOT
リクエスト処理量 毎秒の完了リクエスト数 長さ分布、バッチ、スケジューリング
トークン処理量 毎秒の総生成トークン数 GPU利用率、並列化、カーネル
同時実行数 同時に扱う活動中の系列数 KV Cache、メモリ、スケジューリング
リクエスト単価 GPU時間または金銭的費用 モデル、長さ、キャッシュ、利用率

トークン効率は、成功したタスク当たりの入出力数、キャッシュ命中、再試行、成功一件の費用にも分解できます。

典型的なトレードオフ

  • 大きいバッチは総処理量を増やしやすいが、待ち時間や個別遅延も増え得る。
  • Tensor Parallelは大モデルを載せられるが、デバイス間通信を伴う。
  • 長い文脈はPrefillとKV容量を増やす。
  • 量子化はメモリ・帯域を節約するが、品質とカーネル対応の確認が必要。
  • Speculative DecodingはDraft側の計算を追加し、Target側の生成反復を減らす。

連続バッチ処理とスケジューリング

Static Batchingでは一組を固定し、全体が終わるまで資源を保持する場合があります。短い出力が長い出力に引きずられます。Continuous Batchingは反復ごとに完了系列を除き、空いた枠へ新規リクエストを入れてGPUとキャッシュを活用します。

実行の流れ

等待队列
  → Scheduler 选择可进入的 Prefill/Decode 请求
  → 执行一个或若干 iteration
  → 回收已结束请求的 KV block
  → 加入新请求
  → 下一 iteration

PagedAttentionやPaged KV Cacheと組み合わせ、各系列に最大の連続領域を予約せず、ブロック単位で動的に確保します。内部断片化を減らし、柔軟な入れ替えを可能にします。

スケジューリングの難しさ

  • 長い入力のPrefillがDecodeを妨げ、TPOTが揺れる。
  • TTFTと生成中の滑らかさの優先順位を決める必要がある。
  • 長さやサンプリング設定によりバッチ形状が変わる。
  • Prefix Cache、LoRA Adapter、テナント優先度が制約を増やす。
  • 高処理量と低い裾の遅延は同義ではなく、p95/p99を確認する。
