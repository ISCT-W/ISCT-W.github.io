ツール呼び出し：モデルの意図と実行権限を分ける

ツール呼び出しは、言語モデルに最新情報の取得や具体的な操作を可能にし、アプリケーションを実際の権限境界へ導きます。

W韋 君豪読了目安 7 分

ツール呼び出しは、言語モデルに最新情報の取得や具体的な操作を可能にし、アプリケーションを実際の権限境界へ導きます。モデルはツール名と引数を提案し、サーバーは操作の可否、再試行の可否、失敗時の扱いを決めます。この責務を分けることで、柔軟性が制御不能な副作用になるのを防ぎます。

図の構造を見る（原文）
flowchart TD
    M["模型生成工具名与参数"] --> S["Schema 与业务语义校验"]
    S --> A["身份、租户、资源与权限校验"]
    A --> B["审批、预算、超时与幂等检查"]
    B --> T["服务端执行工具"]
    T --> R["结构化结果与证据"]
    R --> M
    T --> F["分类记录错误与副作用状态"]
    F --> D{"是否可安全重试"}
    D -->|"是"| B
    D -->|"否"| H["停止、降级或人工处理"]

ループはモデルが判断を続けられることを表しますが、実行のたびに検証します。エラー時はまず権限、引数、副作用の発生状況を確認します。すべての失敗を再試行可能なネットワーク障害として扱ってはいけません。

呼び出しの意図から実行へ

Function Callingでは、モデルがツールSchemaに沿って呼び出し意図を出力し、アプリケーションがAPIを実行して構造化結果を返します。最新データ、計算、業務操作を扱えますが、権限と副作用はサーバーが管理します。

実行の全体像

用户问题
→ 模型选择工具并生成参数
→ Schema 校验
→ 身份、租户、权限和审批
→ 超时、预算与幂等检查
→ 服务端执行工具
→ 结构化 tool result
→ 模型继续规划或生成答案
→ 保存工具轨迹与证据

JSON生成だけでは足りない理由

  • Schemaが検証するのは形であり、業務上の妥当性はサーバーが確認する。
  • モデルが出した user_id や project_id を権限の根拠にしない。
  • 副作用のあるツールには必要に応じた承認、冪等キー、補償処理が必要。
  • 読み取り専用でもテナント、結果サイズ、機微フィールドを制限する。
  • 結果にプロンプトインジェクションが含まれ得るため、信頼できないデータとして扱う。
  • ステップ上限、呼び出し予算、キャンセル、復旧も必要。

エンジニアリングへの応用

静的に登録した業務ツール、厳格な引数Schema、範囲を限定したTool Context、人による承認を組み合わせられます。引用や業務カードは成功したツール結果から作り、実行を検証可能な出力へ結び付けます。

決定的な実行境界で権限を守る

基本は最小権限です。機微情報を公開学習データに入れず、推論時はユーザー、プロジェクト、情報源に基づいてサーバー側で絞り、必要最小限のコンテキストだけを渡します。RAGは入口にすぎず、ACL、ツール権限、インジェクション対策、出力検査、ログ管理が必要です。

層ごとの対策

  1. 学習・モデル層： 学習データの分類、秘密情報の除去、利用許可の確認を行い、canaryや記憶抽出を評価します。機密知識は汎用重みへ固定せず、管理された情報源に置きます。
  2. 検索層： 検索前にテナント・ユーザー・文書のACLを適用します。キャッシュキーには権限範囲とデータ版を含め、必要なチャンクだけを返し、認証情報や機微フィールドを除きます。
  3. Agent・Tool層： サーバーでツールを静的登録し、ユーザーごとに絞ります。高リスクの読み取りや副作用には適切な承認を設け、任意URL、Shell、SQL、外向き通信を制限します。Webページ、添付、ツール結果は信頼できないデータとして扱い、間接的なインジェクションを防ぎます。
  4. 出力・運用層： DLP/PII検査とマスキングを行い、生の認証情報や機微なプロンプト全体をログに残しません。アクセス主体、情報源、ツール、判断を記録し、漏えいと越権のレッドチーム評価を定期的に実施します。

エンジニアリングへの応用

プロジェクトの役割、ブランドの共有範囲、情報源のライセンス、ツール承認を層に分けて実装すれば、モデルの判断と業務上の権限を分離できます。

タスク・根拠・安全性・システムを分けて評価する

モデルの点数だけでなく、タスクの結果、根拠、安全性、システムの振る舞いへ評価を広げます。オフラインの正解集は能力を、オンライン指標は利用者が実際に目的を達成したかを示します。両方を場面別に分け、回帰を追跡します。

評価のマトリクス

観点 指標の例
タスク品質 Exact Match、F1、成功率、人の選好
有用性 網羅性、実行可能性、利用者の解決率
事実性 事実の正答率、主張の検証
根拠との整合 コンテキストの支持率、引用の適合率・再現率
検索 Recall@k、MRR、NDCG、ゼロ件率
頑健性 誤字、言い換え、長い文脈、分布外入力
安全性 有害性、越権、プライバシー、脱獄、誤拒否率
Agent ツール選択、引数の正確さ、手順数、復旧率
効率 TTFT、TPOT、p95遅延、トークン、費用、スループット
運用 エラー、再試行、キャッシュ命中、ロールバック、ドリフト

LLM Judgeの使い方

自由記述の回答を大量に一次評価する際には便利ですが、次を確認します。

  • 評価基準を明確にし、観点ごとに採点する。
  • 候補の順をランダムに変え、位置バイアスを測る。
  • モデル名を隠し、文体への好みを抑える。
  • 人のラベルを使って一致度を校正する。
  • 重要な安全性や事実性は、ルール、ツール、人で再確認する。
  • Judgeのモデルとプロンプトの版を記録する。

評価の流れ

定义真实任务和失败成本
→ 建立黄金集与困难切片
→ 对各模块分别测量
→ 端到端回放
→ 人工复核高风险样本
→ 灰度/A-B 测试
→ 监控漂移并把失败样本回流

エンジニアリングへの応用

画像レビューなら、キャラクター認識、ルールの計画、矩形、素材検索、幾何検証、最終指摘に分けて評価できます。Agentならツール選択、権限、根拠、成功率、トークン、遅延を測ります。
