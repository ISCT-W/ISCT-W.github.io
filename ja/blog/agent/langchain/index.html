LangChain：コンポーネントの境界を明確にして LLM アプリを作る

すべてのアプリに自律的な計画を行う Agent が必要なわけではありません。

W韋 君豪読了目安 12 分

すべてのアプリに自律的な計画を行う Agent が必要なわけではありません。単発呼び出し、固定検索フロー、モデルが選ぶツールループでは、複雑さと失敗の仕方が異なります。LangChain はモデル、メッセージ、ツール、検索部品を提供しますが、抽象化は状態、復旧要件、保守負担に合わせて選びます。

図の構造を見る（原文）
flowchart TD
    I["应用任务与执行约束"] --> C{"执行路径是否预先确定"}
    C -->|"是"| W["Prompt、Model、Parser 等组件串联"]
    C -->|"模型需要选择动作"| A["Agent 模型与工具循环"]
    W --> O["校验结果、评估质量与成本"]
    A --> O
    I --> P{"是否需要持久化、审批或复杂分支"}
    P -->|"是"| G["用 LangGraph 显式组织状态与执行"]
    P -->|"否"| S["选择足够简单的 SDK 或组件组合"]

部品の再利用、モデルの判断、永続実行は異なる要件です。固定フローでも同じ部品を使えますが、複雑な状態管理をモデル呼び出しの追加だけで代替することはできません。

本記事は 2026 年 8 月の公式 Python 文書に基づきます。API は変化するため、利用時には言語、版、モジュールを確認してください。

抽象化が解く問題を先に定める

コンポーネントと状態実行基盤の分担

LangChain はモデル、メッセージ、ツール、Retriever、Prompt、Middleware、構造化出力、Agent の高水準部品を提供します。LangGraph は State、Node、Edge を中心に、分岐、ループ、永続化、停止・再開、長い処理、人の介入を扱います。

create_agent 自体も LangGraph 上で動作します。競合する選択肢ではなく、LangChain の部品を必要に応じて明示的なグラフで編成できます。単発の Prompt→Model→Parser には通常グラフは不要で、承認、復旧、検証ループ、複数の決定的段階で価値が高まります。

状態を持つ実行基盤の費用と利点

分岐とループは Python だけでも書けます。LangGraph の価値は図を描くことより、更新、並行マージ、チェックポイント、Thread 復旧、Interrupt、Streaming、観測可能な実行を共通プロトコルで扱えることです。

短く復旧不要なら通常コードが簡単です。数分から数時間のタスク、人の承認、途中再開、履歴確認、並行ノードが必要なら、自作基盤の負担を減らせます。

単純な実装を保てる条件

数個の固定関数で足りる、極低遅延が必要、業務フローを決定的にしたい、SDK の一部しか使わない、抽象化が重要な機能やエラーを隠す、といった場合は導入しない選択もあります。履歴書のキーワードではなく、複雑さ、交換可能性、復旧、観測の要件で判断します。

Workflow と Agent の実行方式

固定経路と実行時の行動選択

Chain は開発者が主に経路を定め、Agent はモデルがツール選択、追加処理、終了を判断します。前者はテスト、遅延、費用を予測しやすく、後者は意図や手順数が変わる問題に向きます。外側を決定的 Workflow、局所を Agent にする構成も一般的です。

LLM を一度呼ぶだけで Agent とはいえません。モデルによる行動選択または反復判断が区別の要点です。

モデル、ツール、観測のループ

メッセージとツールをモデルへ渡すと、最終回答か Tool Call が返ります。実行基盤が検証してツールを実行し、結果を履歴へ加え、完了または停止条件まで判断を繰り返します。

図の構造を見る（原文）
flowchart LR
    U["User message"] --> M["Model"]
    M -->|"final answer"| E["End"]
    M -->|"tool call"| V["Schema / policy validation"]
    V --> T["Tool execution"]
    T --> R["Tool result message"]
    R --> M

本番ではステップ、Token、時間、並行ツール数、副作用の権限を制限し、無限ループや費用増大を防ぎます。

合成、並行処理、結果の配信

Runnable で処理単位を組み合わせる

LCEL は | などで実行部品をつなぐ表現です。基礎となる Runnable は呼び出し、バッチ、Streaming、非同期、合成に対応します。

chain = prompt | model | parser

RunnableSequence は出力を順に渡し、RunnableParallel は同じ入力で独立分岐を並行実行します。明確なデータフローは LCEL、複雑なループや状態分岐、復旧は LangGraph が適します。

同期、非同期、バッチ、ストリーミング

invoke は単一入力の同期、ainvoke は I/O 向きの非同期呼び出しです。batch/abatch は独立入力群を扱い、スレッドプール、asyncio.gather、連携先のネイティブバッチなどを使います。stream/astream は逐次配信で体感遅延を改善しますが、総計算量を自動的には減らしません。

Timeout、取消、並行数、Backpressure、例外集約も必要です。async だけでスループット向上は保証されません。

依存する直列処理と独立した並行分岐

検索してから回答する処理は直列です。要約とキーワード抽出などは並行化できます。ただし瞬間 QPS、Rate Limit、結果統合、部分失敗への対処が増え、同じ外部資源へ書く場合は並行安全性も必要です。

再試行を最小の安全な境界に置く

一時的な API 失敗など、再実行が安全な単位で retry し、Agent 全体を無条件にやり直しません。Fallback は利用不能なモデル、検索器、提供元を代替します。

非冪等な書き込みは無条件 retry できず、引数・権限などの恒久エラーも指数バックオフ対象ではありません。代替モデルはツール、文脈長、構造化出力が異なる場合があります。再試行は末尾遅延と費用を増やすため、予算と遮断条件を設けます。

Prompt、メッセージ、コンテキスト

テンプレートの役割とデータ境界

PromptTemplate は文字列、ChatPromptTemplate は System/Human/AI/Tool の役割付き列を作ります。境界は指示優先度、キャッシュ、Tool Calling に影響します。変数は信頼できる指示ではありません。ユーザーデータを明示的な位置に入れ、文字列連結でシステム指示に見せかけない設計が必要です。

構造とツール呼び出しの対応を残す

Message は文字列に加え、役割、Tool Call と ID、構造化 Content、応答情報、Token Usage を持ちます。AIMessage.tool_calls と ToolMessage.tool_call_id の対応が必要です。全履歴を文字列化すると、役割、呼び出し関係、マルチモーダル構造、提供元間の共通形式が失われます。

State、Runtime Context、Store

State はメッセージや中間結果など更新される実行データです。Runtime Context はユーザー ID、DB 接続、依存オブジェクトを注入します。Store は Thread をまたぐ好み、記憶、事実を保存します。

接続を State に入れると直列化が難しく、秘密を Checkpoint に保存すると漏えいにつながります。業務 DB を丸ごと Store に複製すれば二重書き込みと整合性の問題が生じます。

ツールと実行時の拡張

ツールの責務、入力、返却形式

良いツールは単一の目的、安定した名前、正確な説明、厳密な Schema、一貫した出力とエラーを持ちます。モデルの選択は名前、説明、引数定義に強く依存します。

列挙値、範囲、業務 ID を検証し、実行内で認証・認可を再確認します。Timeout、retry、結果サイズを制限し、書き込みには冪等キー、承認、Dry Run を用います。生のスタックではなく安定したエラー型を返します。

意図の生成と実行権限を分ける

Tool Calling は名前と引数を持つ要求であり、実行は検証後のアプリが行います。ユーザー、Tenant、資源 ID、承認状態、引数を実行境界で確認します。Schema に項目がないだけで越権を防げるわけではありません。

Middleware で横断的な処理をまとめる

モデル・ツール前後の Hook で動的選択、ログ、retry、fallback、速度制限、PII 検出、Guardrail、要約、人の介入を扱えます。ただし重要な業務状態遷移を隠してはいけません。順序を記録して各層を検証し、過剰な Hook でエラー伝播を不透明にしないことが大切です。

権限と段階で利用可能ツールを選ぶ

静的ツールは作成時に固定され、単純で検証しやすい構成です。動的ツールは権限、段階、文脈、モデル能力で絞り、選択肢と露出を減らします。ただし非表示は実行時認可の代わりにはなりません。頻繁な変更は Prompt Cache や挙動の安定性にも影響します。

構造化結果と検索部品

提供元の制約とツール方式

ProviderStrategy はネイティブ構造化出力、ToolStrategy は Tool Calling を使います。create_agent(response_format=Schema) は能力に応じて選択します。どちらでも検証失敗、複数出力、retry 上限、業務意味を扱う必要があります。Schema を通っても内容が正しいとは限りません。

構文の後にも業務検証が必要

利用できればネイティブ構造化出力、次に Tool Calling、最後に自由文 JSON/正規表現解析を検討します。自由文は Markdown、説明、途中切断に弱い方式です。日付の実在、ID の存在、金額上限は決定的な業務検証で確認します。

オフラインとオンラインの検索経路

オフラインでは読み込み、洗浄・解析、分割、Embedding、索引化を行います。オンラインでは質問理解、Retriever/混合検索、再順位付け・圧縮、文脈構成、生成、引用検証を行います。部品交換が容易でも RAG 品質は保証されず、召回、順位、文脈利用、根拠との一致を分けて評価します。

Retriever と Vector Store

Vector Store はベクトル保存・検索を担い、Retriever は Query から Document 列を返す広いインターフェースです。BM25、企業検索、Web、DB、複合検索も包めるため、Retriever 利用はベクトル DB や意味類似検索だけを意味しません。

固定検索、Agentic RAG、混合フロー

2-Step RAG は先に検索して生成します。Agentic RAG はモデルが検索時機、ソース、質問書き換え、再検索を判断します。Hybrid RAG は権限フィルターと基本検索を必須にし、その後の深掘りを Agent に任せるなどの組み合わせです。

根拠が必要な高リスク業務では、モデルの自主的検索だけに依存せず、必要な検索や DB 確認を強制し、裏付けがなければ回答を控えます。

文書構造と評価で分割を選ぶ

細かな召回と十分な意味保持を両立する大きさが必要です。Overlap は境界損失を減らしますが、索引、重複、Context Token を増やします。コードは関数・クラス、Markdown は見出し、契約は条項、表は見出しとの関係を保ちます。一般文書は RecursiveCharacterTextSplitter を出発点に、回答を含むチャンクの召回、最終品質、費用で調整します。

実際の実行要件で技術を選ぶ

検索、検証、承認、実行、保存が明示的に分かれ、承認が要求をまたぎ、途中から復旧するなら、LangGraph の状態遷移と LangChain 部品が役立ちます。

モデルとツールのループが中心なら、SDK の Streaming、フロント連携、保守負担に合う薄い実行基盤が適する場合もあります。図で表現することと、永続実行、Interrupt、複雑な分岐を実装することは別です。概念の類似ではなく実際の機能で比較します。
