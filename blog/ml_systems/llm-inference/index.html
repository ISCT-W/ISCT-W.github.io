LLM 推理：KV Cache、连续批处理与服务性能

拆解自回归缓存的计算与显存成本，区分首个输出、逐步生成和整体吞吐，再分析连续批处理的收益与调度约束。

W韦君豪约 5 分钟

推理优化不只有生成速度一个数字。长输入带来的预填充计算、逐步生成的缓存访问，以及多个请求共享设备的调度方式，会同时影响响应延迟、吞吐和显存。需要先区分这些成本的来源，再判断缓存、量化、批处理或并行优化解决的是哪一段瓶颈。

连续批处理在生成迭代之间调整活动请求，而不是一直等待固定的一批全部完成。预填充与逐步生成仍会争用资源，吞吐增加并不自动意味着首个输出或尾延迟更低。

KV Cache 消除的是历史前向的重复计算

生成第 (t) 个 token 时，前 (t-1) 个 token 在各层的 Key 和 Value 不会改变。KV Cache 保存这些张量，新一步只计算新 token 的 Q/K/V，并让新 Query 关注缓存中的全部 Key/Value，从而避免每一步重新运行整个前缀。

计算与显存

若不缓存，每一步都重新计算长度不断增长的完整序列；缓存后，历史 token 的线性投影和前层计算不再重复。第 (t) 步的 Attention 仍需让新 Query 与 (t) 个 Key 做计算，所以单步 Attention 随上下文长度近似 (O(t))，完整生成阶段的 Attention 总量仍近似 (O(T^2))。KV Cache 主要消除的是历史 token 的重复前向计算，而不是把整个长序列 Attention 变成严格 (O(T))。

KV Cache 显存可粗略估算为：

MKV=2×L×T×Hkv×dhead×b×BM_{KV}=2\times L\times T\times H_{kv}\times d_{head}\times b\times BMKV​=2×L×T×Hkv​×dhead​×b×B

其中 2 表示 K/V，(L) 为层数，(T) 为缓存长度，(H_{kv}) 为 KV Head 数，(b) 为每元素字节，(B) 为 Batch/并发序列数。

优化方式

  • MQA/GQA：多个 Query Head 共享较少的 KV Head；
  • KV Quantization：用 FP8/INT8 等降低缓存精度；
  • Paged KV Cache：按页管理，减少预留和碎片；
  • Sliding Window/Chunked Attention：限制有效历史范围；
  • Prefix Cache：相同 Prompt 前缀跨请求复用；
  • KV Offload：将部分缓存移到 CPU/其他层级，换取带宽开销。

性能必须同时看延迟、吞吐与成本

至少要同时看延迟、吞吐、并发、显存和单位成本，而且区分 Prefill 与 Decode。单报“tokens/s”没有意义，必须说明是单请求还是整卡、输入/输出长度、Batch 和分位数。

核心指标

指标 含义 主要影响因素
TTFT 从请求到第一个输出 token Queue、Prompt 长度、Prefill、调度
TPOT / ITL 相邻输出 token 的平均时间 Decode、KV 带宽、Batch、通信
E2E Latency 完整回答耗时 TTFT + 输出长度 × TPOT
Request Throughput 每秒完成请求数 长度分布、Batch、调度
Token Throughput 每秒生成总 token 数 GPU 利用率、并行、Kernel
Concurrency 同时服务的活动序列数 KV Cache、显存和调度
Cost/Request 单请求 GPU 时间或货币成本 模型、长度、缓存、利用率

“Token Efficiency” 可以进一步拆为：完成一个合格任务所需的输入/输出 token、缓存命中、重试次数以及单位成功任务成本。

典型权衡

  • 增大 Batch 往往提高总吞吐，但可能增加 Queue 和单请求延迟；
  • Tensor Parallel 可以容纳大模型，但带来跨卡通信；
  • 更长上下文增加 Prefill 计算与 KV Cache；
  • 量化降低显存和带宽，但要验证精度与 Kernel 支持；
  • Speculative Decoding 用额外 Draft 计算换取更少 Target Model Decode 步骤。

连续批处理与请求调度

Static Batching 把一组请求固定在一起，通常要等整组完成才能释放资源；不同输出长度导致短请求被长请求拖住。Continuous Batching 在每个 Decode iteration 后移除已完成序列，并立即把新请求加入可用槽位，提高 GPU 和 KV Cache 利用率。

执行方式

等待队列
  → Scheduler 选择可进入的 Prefill/Decode 请求
  → 执行一个或若干 iteration
  → 回收已结束请求的 KV block
  → 加入新请求
  → 下一 iteration

Continuous Batching 常与 PagedAttention/Paged KV Cache 配合：不为每个序列预留最大连续显存，而是按 block 动态分配，减少内部碎片，并允许更灵活地换入换出。

调度难点

  • 长 Prompt Prefill 可能阻塞 Decode，引起 TPOT 抖动；
  • 需要在 TTFT 与 Decode 流畅度之间选择优先级；
  • 不同长度和采样参数会造成 Batch 形状变化；
  • Prefix Cache、LoRA Adapter 和多租户优先级会增加调度约束；
  • 高吞吐并不自动等于低尾延迟，需要观察 p95/p99。
