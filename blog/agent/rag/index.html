RAG：把检索结果变成可以核对的回答

沿数据、检索、重排、生成与引用定位幻觉，讨论企业级检索链路、小模型选择，以及推理计算能够和不能解决的问题。

W韦君豪约 7 分钟

RAG 的价值是让模型使用可更新的外部知识，但从文档进入系统到答案交付，中间仍有一连串可能失真的环节。可靠性因此不能只看召回率，也不能只看回答是否附有链接。需要把知识来源、上下文组织、生成约束与引用验证分别设计，再把失败追溯到具体阶段。

flowchart TD
    D["文档接入、解析与版本"] --> I["结构感知分块与索引"]
    Q["用户问题"] --> P["权限与元数据范围"]
    P --> R["混合检索"]
    I --> R
    R --> K["重排与上下文压缩"]
    K --> E{"证据是否足以回答"}
    E -->|"是"| G["生成回答并逐项绑定来源"]
    G --> V["核对结论与引用的支持关系"]
    E -->|"否"| U["澄清、换工具或返回未知"]

检索只是证据链的一段。图中的检查点分别约束可访问的数据、进入上下文的证据，以及最终结论是否由来源支持；没有答案的检索结果不应被包装成确定结论。

幻觉来自哪一层

LLM 的训练目标是预测条件分布中的下一个 token，而不是查询一个始终正确的事实数据库。知识缺失、Prompt 含糊、训练冲突、长上下文利用不足和解码策略都可能让模型生成语言连贯但无证据的答案。缓解幻觉需要从知识来源、生成约束、验证和拒答四层设计，而不是只调低 Temperature。

原因分类

  1. 模型知识问题：预训练数据没有该事实、事实过时或来源冲突；
  2. 输入问题：问题前提错误、指代不清或要求超出可用上下文；
  3. 生成目标问题：模型被训练为尽量回答，缺少“证据不足时停止”的行为；
  4. 上下文利用问题：检索证据太长、位置靠后、相互矛盾或被无关信息淹没；
  5. 解码问题：较高随机性增加输出变化，但贪心/低温同样可能稳定地产生错误事实；
  6. 工具和数据问题：上游搜索、OCR、数据库或 API 已经返回错误结果。

缓解方法

  • 用 RAG、数据库或业务工具提供可更新知识；
  • 把候选实体限制在 closed set，使用结构化 ID；
  • 让回答关联引用，并检查 claim 是否由证据支持；
  • 对数字、日期、计算和权限敏感事实使用确定性工具；
  • 采用 Schema/Constrained Decoding 限制输出结构；
  • 增加 verifier、self-consistency 或第二模型复核；
  • 明确“证据不足/工具失败时返回 unknown”；
  • 将检索质量与生成质量分开评估。

降低 Temperature 主要减少随机性；CoT 可能帮助多步推理，但两者都不是事实性保证。

工程应用

一种可行设计是让引用由成功工具结果派生，并使用限定的角色或素材候选集、规则数据库和几何验证，把高风险事实从自由文本生成迁移到确定性证据协议。

从检索到引用的失败链路

RAG 只是把外部上下文放入生成过程，检索和生成两个阶段都可能失败。正确文档没有被召回、分块丢失条件、Rerank 排错、上下文相互冲突、模型忽略证据或在无答案时强行回答，都会造成 RAG 幻觉。

失败链路

阶段 典型失败 对应诊断指标
Ingestion OCR 错误、表格结构丢失、旧版本混入 文档覆盖率、解析准确率
Chunking 条件与结论被拆开、Chunk 过大/过小 Answer-bearing chunk 可召回率
Retrieval Query 不匹配、向量语义偏移、权限过滤后无结果 Recall@k、MRR、无结果率
Rerank 正确文档被降权 NDCG、Top-k 命中
Context 证据太长、冲突、lost-in-the-middle Context precision、位置消融
Generation 模型使用参数记忆覆盖证据、错误归因 Faithfulness/Groundedness
Citation 引用存在但不支持对应 claim Citation precision/recall

改进方式

  • Query rewrite、multi-query、metadata filter 和 hybrid retrieval；
  • Parent-child、sentence-window 或结构感知分块；
  • Cross-encoder/LLM rerank；
  • 在生成前判断 context 是否含答案；
  • 要求按 claim 给引用，并做引用蕴含检查；
  • 证据冲突时展示来源和时间，不强行合并；
  • 检索无结果时触发澄清、换工具或拒答；
  • 将网页/文档视为不可信输入，处理 Prompt Injection。

把 RAG 组织成可维护的系统

企业级 RAG 是数据、检索、生成、权限、评估和运维共同组成的系统。核心链路为：

数据接入与版本
→ 解析/OCR/清洗
→ 结构感知分块
→ Embedding + 关键词/结构化索引
→ 权限与元数据过滤
→ Query 理解/改写
→ Hybrid Retrieval
→ Rerank 与上下文压缩
→ 生成、引用与拒答
→ 评估、反馈和可观测性

各层要点

数据层

  • 为文档保存 owner、tenant、版本、生效时间和权限；
  • PDF、表格、图片、代码使用不同解析策略；
  • 去重并保留父子结构、章节和页码；
  • 更新或删除文档时同步清理索引。

索引层

  • Dense Embedding 捕捉语义相似；
  • BM25/关键词覆盖专有名词、ID 和精确短语；
  • 结构化字段进入 metadata filter；
  • 根据数据规模选择 HNSW、IVF 或托管向量库；
  • Embedding 模型升级需要索引版本管理。

检索层

  • 识别问题类型和时间范围；
  • Query Rewrite、Decomposition 或 Multi-hop Retrieval；
  • Hybrid 分数融合；
  • Cross-encoder/LLM Rerank；
  • 去重、上下文压缩和 token 预算。

生成层

  • 明确回答必须基于哪些 Context；
  • 逐 claim 绑定来源；
  • 缺少证据时澄清或返回未知；
  • 工具结果和文档文本使用不同信任级别；
  • 使用结构化输出支持后续程序处理。

平台层

  • 多租户和文档级 ACL；
  • 缓存键包含用户/项目/权限范围；
  • 记录 Query、召回、Rerank、引用、Token、延迟和错误；
  • 离线黄金集与在线反馈共同驱动改进；
  • 敏感字段脱敏、审计日志和数据保留策略。

证据质量与模型规模的取舍

当正确证据已经被检索出来，生成任务可能主要是抽取、归纳、改写或结构化输出，小模型可以以更低延迟和成本完成。但“小模型更听话、更不幻觉”不是普遍规律，效果取决于上下文长度、任务复杂度、语言、指令遵循和训练数据。

适合 SLM 的场景

  • 固定 Schema 抽取与分类；
  • 单文档、短上下文问答；
  • 高并发、低延迟的内部助手；
  • 边缘部署或敏感数据本地推理；
  • 通过蒸馏针对特定任务优化；
  • Router 已把复杂问题分配给更强模型。

仍需要较大模型的场景

  • 多文档冲突消解和跨文档推理；
  • 多跳检索、复杂规划和工具协同；
  • 长上下文中的细粒度证据整合；
  • 低资源语言或专业领域理解；
  • 高质量解释与开放式写作。

评估方式

不要只比较单题准确率，还要看：任务成功率、引用正确性、拒答率、TTFT/TPOT、单位请求成本、峰值并发和升级到大模型的比例。

推理计算的收益与事实性边界

CoT 通过产生中间步骤，为多步算术、符号推理和规划提供更多测试时计算，使模型不必在一次 token 跳转中直接得到结论。它的代价是输出 token、延迟和错误传播增加，而且生成的解释未必忠实反映模型真实决策过程。

更完整的理解

  • Few-shot CoT 提供带推导的示例；
  • Zero-shot CoT 使用类似“分步骤思考”的提示；
  • Self-consistency 采样多条推理路径后对答案投票；
  • Reasoning Model 可能在训练和推理阶段使用更长的内部推理；
  • Agent scratchpad 可以记录计划和工具观察，但不等于应向用户展示全部内部推理。

现代产品通常向用户提供简洁、可验证的理由或计算步骤，而不是暴露原始隐藏推理。系统安全也不能依赖“隐藏 CoT”：敏感信息不应进入模型可见上下文，System Prompt、工具和数据还需独立权限保护。

代价和风险

  • Token 与延迟上升；
  • 错误中间步骤会锚定后续答案；
  • 推理文本可能听起来合理但并不 faithful；
  • 对简单问题强制 CoT 反而增加噪声；
  • 将内部敏感上下文复制到可见解释会造成泄露。
