LangChain：用清晰的组件边界构建 LLM 应用

从固定链路与 Agent 决策的区别出发，展开模型、消息、工具、检索和结构化输出组件，并说明并发、重试与技术选型的取舍。

W韦君豪约 12 分钟

应用需要的并不总是一个能够自行规划的 Agent。单次调用、固定检索链路、模型驱动的工具循环，拥有不同的复杂度和失败方式。LangChain 提供模型、消息、工具与检索等组件，使这些工作单元可以组合；选择抽象时仍应以状态复杂度、恢复要求和维护成本为依据。

组件复用、模型决策和持久执行是不同层面的需要。固定流程可以使用相同模型与工具组件，复杂状态管理则需要额外的运行时协议，不能仅靠增加一次模型调用来替代。

接口与机制以 2026 年 8 月的官方 Python 文档为依据。具体 API 会继续演进，使用时需要核对语言、版本和模块。

先确定抽象解决的问题

组件抽象与状态运行时的分工

LangChain 提供模型、消息、工具、Retriever、Prompt、Middleware、结构化输出和 Agent 等高层抽象；LangGraph 提供以 State、Node、Edge 为核心的低层有状态编排运行时，重点解决循环、分支、持久化、暂停恢复、长流程和 Human-in-the-loop。

当前 LangChain 的 create_agent 底层运行在 LangGraph 上。因此二者不是简单竞争关系：常见做法是用 LangChain 的模型/工具组件，在需要显式控制时使用 LangGraph 编排。

如果只是单次“Prompt → Model → Parser”，通常不需要 LangGraph；如果流程包含审批、恢复、循环校验或多个确定性阶段，LangGraph 的价值才明显。

有状态编排的成本与收益

普通 Python 完全可以写分支和循环。LangGraph 的主要价值不是“能画图”，而是把状态更新、并发合并、检查点、线程恢复、Interrupt、Streaming 和可观测执行统一成运行时协议。

如果流程短、无恢复要求、团队能够维护普通代码，直接 Python 可能更简单。若任务跨分钟/小时、需要人工审批、失败后从中间恢复、查看历史状态或并行执行多个节点，LangGraph 能减少自建基础设施。

保持简单实现的条件

以下场景往往不需要：

  • 单次模型调用或两三个固定函数即可完成；
  • 极低延迟路径无法接受框架层开销；
  • 业务需要严格确定性，模型不应决定流程；
  • 团队只需要供应商 SDK 的少量能力；
  • 为了统一抽象反而隐藏了供应商关键能力或错误信息。

选择框架要基于复杂度、可替换性、恢复和可观测需求，而不是因为简历上需要关键词。

工作流与 Agent 的执行方式

固定工作流与运行时动作选择

Chain 的执行路径主要由开发者预先确定；Agent 在运行时让模型根据当前消息和工具结果决定是否调用工具、调用哪个工具以及何时结束。

  • Chain 更可预测、容易测试、延迟与成本上限更清楚；
  • Agent 更灵活，适合用户意图和步骤数不固定的问题；
  • 生产系统常采用混合方式：外层确定性 Workflow，局部节点允许 Agent 决策。

不能把“调用了一次 LLM”称为 Agent。至少应存在模型驱动的动作选择或循环决策。

模型、工具与观察构成的执行循环

核心循环是：把消息和可用工具交给模型；模型要么产生最终回答，要么产生 Tool Call；运行时校验并执行工具，将 Tool Result 追加到消息；模型读取结果后继续决策，直到不再调用工具或触发停止条件。

生产实现还要限制最大步数、总 Token、总时间、并行工具数和副作用权限，避免无限循环或成本失控。

组合、并发与交付方式

用 Runnable 组合工作单元

LCEL（LangChain Expression Language）是用 | 等组合方式连接可执行组件的表达形式。其底层统一抽象是 Runnable：一个工作单元可以被调用、批处理、流式执行、异步执行和继续组合。

典型组合是：

chain = prompt | model | parser

RunnableSequence 串行传递上一步输出，RunnableParallel 对同一输入并行运行多个分支。LCEL 适合数据流明确的 Chain；复杂循环、有状态分支和恢复通常更适合 LangGraph。

同步、异步、批处理与流式接口

回答：

  • invoke：同步处理单个输入；
  • ainvoke：异步处理单个输入，适合 I/O 密集调用；
  • batch/abatch：批量处理多个独立输入，默认实现可能使用线程池或 asyncio.gather，具体集成可提供原生批处理优化；
  • stream/astream：边生成边消费输出，改善用户感知延迟，但不自动减少总计算量。

使用时应补充超时、取消、并发上限、Backpressure 和异常聚合，不能把“用了 async”直接等同于吞吐一定提高。

串行依赖与并行分支

前者用于存在数据依赖的串行步骤；后者用于互不依赖、可以同时计算的分支。例如同时生成摘要和关键词可以并行，但“先检索再回答”必须串行。

并行的代价包括更高瞬时 QPS、Rate Limit 风险、结果合并和部分失败处理。若多个分支写同一外部资源，还要额外解决并发安全。

把重试放在最小安全边界

重试应放在最小的、确认可安全重试的边界，例如临时性模型/API 调用，而不是盲目重跑整个 Agent。Fallback 用于主模型、主检索器或主供应商不可用时切换备选实现。

注意：

  • 非幂等写操作不能无条件重试；
  • 参数错误、权限错误等永久性失败不应指数退避重试；
  • Fallback 模型可能不支持相同工具、上下文长度或结构化输出；
  • 重试会放大尾延迟和成本，需要预算与熔断。

提示、消息与上下文

提示模板中的角色与数据边界

PromptTemplate 主要生成字符串；ChatPromptTemplate 生成带 System、Human、AI、Tool 等角色的消息序列，更符合 Chat Model API。角色与消息边界会影响供应商的指令优先级、Prompt Cache 和 Tool Calling。

模板变量仍然是不可信输入。用户文本应放入明确的数据位置，不能用字符串拼接让用户内容伪装成 System Instruction。

保留消息的结构与调用关系

Message 不只是文本，还携带角色、Tool Call、Tool Call ID、结构化 Content Block、响应元数据和 Token Usage。Agent 循环依赖 AIMessage.tool_calls 与对应 ToolMessage.tool_call_id 正确配对。

如果把全部历史压成普通字符串，容易丢失角色边界、工具调用关系和多模态结构，也不利于供应商间规范化。

State、Runtime Context 与 Store 的职责

回答：

  • State：本次 Thread/Workflow 中会随节点更新的可变数据，如消息、计划和中间结果；
  • Runtime Context：调用期间注入但不应成为图状态的数据，如当前用户 ID、数据库连接或依赖对象；
  • Store：跨 Thread 持久化的应用数据，如用户偏好、长期记忆或共享事实。

将数据库连接塞进 State 会导致序列化问题；把密码写入 Checkpoint 会形成敏感数据泄漏；把所有业务数据库数据复制进 Store 也会造成双写和一致性问题。

工具与运行时扩展

工具的职责、输入与返回协议

好的 Tool 应具有单一清晰职责、稳定名称、准确描述、严格输入 Schema、明确返回结构和可观察错误。模型主要依据 Tool 名称、描述和参数 Schema 决定是否调用，因此含糊描述会直接降低工具选择准确率。

工程上还应做到：

  • 参数使用枚举、范围和业务 ID 校验；
  • Tool 内部重新执行身份与权限校验，不能相信模型；
  • 设置超时、重试和结果大小上限；
  • 写操作使用幂等键、审批或 Dry Run；
  • 返回稳定的错误类型，而不是把堆栈直接塞回模型。

调用意图与执行权的分离

不是。Tool Calling 是模型生成“工具名 + 参数”的结构化请求；Tool Execution 是应用程序校验请求后真正调用函数或外部系统。模型表达的是意图，执行权仍属于服务端。

因此安全边界必须放在执行层：检查当前用户、Tenant、资源 ID、审批状态和参数；不能因为 Tool Schema 中没有某字段，就认为模型不可能越权。

用 Middleware 集中处理横切逻辑

Middleware 在 Agent 的模型调用、工具执行等关键步骤前后提供 Hook，用来集中实现动态 Prompt/模型/工具选择、日志、重试、Fallback、速率限制、PII 检测、Guardrail、摘要和 Human-in-the-loop。

它适合横切关注点，但不应隐藏关键业务状态转换。Middleware 过多会让调用顺序和错误传播难以理解，应记录执行顺序并为每层写测试。

按权限和阶段选择可用工具

静态工具在创建 Agent 时固定，简单且易测试；动态工具根据用户权限、任务阶段、上下文或模型能力在运行时筛选。动态工具可以减少模型选择空间并阻止暴露无权工具。

但工具隐藏不是权限控制的替代品：即使某工具没有提供给模型，工具执行入口仍必须校验权限。工具集合频繁变化还会影响 Prompt Cache 和模型行为稳定性。

结构化结果与检索组件

供应商约束与工具策略的结构化输出

ProviderStrategy 使用模型供应商原生的结构化输出约束，通常可靠性更高；ToolStrategy 通过 Tool Calling 让模型按 Schema 返回结构化数据，适用于支持工具但没有原生结构化输出的模型。

当前 create_agent(response_format=Schema) 会根据模型能力选择策略。无论哪种策略，都要处理 Schema Validation Error、多个结构化输出、重试上限和业务语义校验。通过了 JSON Schema 不代表字段值在业务上正确。

语法约束之后仍需要业务校验

能使用供应商原生结构化输出时，通常优先使用；其次是 Tool Calling；最后才是从自由文本中解析 JSON/正则。自由文本 Parser 最脆弱，容易受 Markdown、解释文字和截断影响。

但结构化输出只解决语法与类型约束。日期是否真实、ID 是否存在、金额是否超限仍需确定性业务校验。

检索组件的离线与在线链路

常见离线链路为 Document Loader → 清洗/解析 → Text Splitter → Embedding → Vector Store；在线链路为 Query 理解 → Retriever/混合搜索 → Rerank/压缩 → Prompt Context → Model → 引用/验证。

LangChain 的模块化抽象便于替换组件，但不会自动保证 RAG 质量。需要分别评估召回、排序、上下文利用和回答 Groundedness。

Retriever 接口与向量存储

Vector Store 负责保存和按向量搜索数据；Retriever 是“输入非结构化 Query，返回 Document 列表”的更广接口。Retriever 可以由 Vector Store 转换，也可以封装 BM25、企业搜索、Web Search、数据库或组合检索。

因此“用了 Retriever”不等于“用了向量数据库”，也不等于“检索只有 Semantic Similarity”。

固定检索、Agentic RAG 与混合流程

回答：

  • 2-Step RAG：固定先检索再生成，延迟和行为容易控制；
  • Agentic RAG：模型决定何时检索、用哪个数据源、是否改写 Query 或重复检索；
  • Hybrid RAG：把确定性检索步骤与 Agent 决策结合，例如先做强制权限过滤和基础召回，再允许 Agent 深挖。

高风险业务通常不应完全依赖模型“自觉检索”。需要证据的问题可以强制走检索或数据库工具，并在无证据时拒答。

按文档结构与评估选择分块

Chunk 要足够小以便精确召回，又要足够大以保留回答所需语义。Overlap 可以减少边界截断，但会扩大索引、制造重复召回并增加 Context Token。

选择应基于文档结构和评测：代码按函数/类，Markdown 按标题，合同按条款，表格保留表头关系。通用文本可从 RecursiveCharacterTextSplitter 起步，再通过 Answer-bearing Chunk Recall、最终回答质量和成本调参。

技术选型落在实际执行需求上

当流程包含显式检索、校验、审批、执行和结果落库阶段，审批可能跨请求暂停，失败后又需要从中间恢复时，可以用 LangGraph 表达状态和状态转移，并让 LangChain 提供模型与工具组件。

如果流程主要是模型与工具循环，现有 SDK 的流式协议、前端集成和团队维护成本可能更适合较薄的运行时。只把图用于表达工作流，与真正实现持久执行、人工中断或复杂分支，是不同的实现深度。架构比较应逐项说明实际能力，不能仅凭概念相似推断运行时具有同样的恢复语义。
