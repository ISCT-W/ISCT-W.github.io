LangGraph：状态、恢复与长流程的执行语义

展开图状态、并行合并、记忆、检查点和人工介入，再讨论节点重放、幂等、流式交付与故障定位中的执行边界。

W韦君豪约 12 分钟

长流程的困难不只是决定下一步调用哪个函数，还包括保存进度、合并并行更新、等待人工输入，以及在故障之后知道哪些操作可以重做。LangGraph 用图状态和持久化协议组织这些行为。理解它需要把执行快照、模型上下文与外部副作用分别看待，尤其不能把恢复理解成从暂停语句的下一行直接继续。

    N --> U["返回状态更新"]

    R --> C["保存 Checkpoint 与下一步信息"]
    C --> D{"继续、结束或等待人工输入"}
    D -->|"继续"| S
    D -->|"结束"| E["交付结果"]

图示强调状态与执行进度被持久化，而不是保存任意局部变量。实际发生 Interrupt 时，运行时保存暂停所需信息；恢复相关节点会重新执行，所以副作用必须在可安全重放的边界内。

本文以 2026 年 8 月官方 Python 文档为依据，具体持久化模式和流式接口应结合所用版本核对。

状态与更新协议

State、Node 与 Edge 的执行约定

State 是共享状态快照及其 Schema；Node 是读取 State 并返回“状态更新”的函数；Edge 决定接下来执行哪些 Node。Node 不需要返回完整 State，只返回发生变化的字段。

最好的 State 保存流程所需的稳定事实和控制字段，而不是把所有临时对象、数据库连接和重复大文本都塞进去。

编译图与运行时配置

Compile 将 Builder 转为可执行图，并进行基本结构检查；Checkpointer、Store、Interrupt/Breakpoint 等运行配置也在这一阶段绑定。编译并不是训练模型或把 Python 转成机器码。

生产中通常在进程启动时编译一次并复用，不能每个请求重新构图和初始化数据库连接。

状态 Schema 的校验与开销

TypedDict 轻量，适合作为常见默认；Dataclass 可提供默认值；Pydantic 支持更强的运行时校验与类型转换，但有额外开销。选择取决于校验需求、性能和团队习惯。

无论使用哪种 Schema，节点返回值、外部 Tool Result 和恢复后的旧 Checkpoint 都可能需要额外业务校验，不能认为类型标注本身阻止了所有脏数据。

Reducer 定义状态合并语义

Reducer 定义某个 State 字段如何将旧值与节点更新合并。没有显式 Reducer 时，更新通常覆盖旧值；列表消息等字段可用 Reducer 追加、去重或按 ID 更新。

Reducer 应尽量满足确定性，并考虑并发更新的顺序敏感性。把两个并行分支都写入没有合适 Reducer 的同一字段，可能触发并发更新冲突或产生不可预测结果。

消息合并需要识别身份与删除

简单相加只能追加，无法按 Message ID 更新既有消息，也难以正确处理删除消息。LangGraph 的消息 Reducer 会负责消息反序列化，并支持追加、替换和 RemoveMessage 等语义。

对于流式 Tool Call、人工修改历史和消息压缩，使用正确的消息合并语义比普通 List 拼接更安全。

路由、并行与终止条件

路由边与 Command 的适用边界

Conditional Edge 把路由逻辑放在独立路由函数中，根据 State 返回下一个 Node；Command 允许 Node 在一次返回中同时给出 State Update 和 goto，适合更新与路由紧密绑定的情况。

为了可读性，纯路由优先使用 Edge；只有当节点结果本身决定跳转且需要同时更新状态时再用 Command。不要让所有节点任意跳转，否则图会退化为难以理解的隐式控制流。

Send 与动态任务展开

Send 用于运行时动态创建多个下游任务，典型是 Map-Reduce：先根据输入生成不定数量的子任务，并行处理，再通过 Reducer 聚合结果。

需要控制 Fan-out 数量、并发上限、单任务超时和聚合结果大小。用户输入若能无限生成 Send，会造成成本和资源攻击。

Super-step 的并行执行模型

LangGraph 的底层执行采用类似 Pregel 的消息传递模型。一个 Super-step 中可以执行多个当前激活且相互独立的任务；步骤结束后合并其 State Update，再决定下一批节点。

这意味着“图上有两条边”不一定严格按代码书写顺序串行执行。并行节点必须避免未声明的数据依赖和非并发安全的副作用。

并行写入的冲突与确定性合并

不同字段可以分别更新；同一字段需要相容的 Reducer。若没有 Reducer 且收到多个更新，运行时通常无法知道应该覆盖哪一个，可能报告并发更新错误。

解决方式是：拆分字段、定义满足业务语义的 Reducer、让分支返回带 ID 的结果后在后续 Join Node 确定性合并，或者明确改为串行。

用多层预算限制循环

同时设置：

  • 图递归/步数上限；
  • Agent Tool Call 上限；
  • 总时间、Token 和成本预算；
  • 重复 Tool+参数检测；
  • 连续无进展检测；
  • 明确终止状态与失败状态。

达到限制时应返回可解释的部分结果或请求人工介入，而不是只抛出一个内部异常。

执行轨迹与记忆

Thread、Checkpoint 与持久化组件

Checkpointer 是保存/加载图状态快照的组件；Thread 是一条独立执行或会话轨迹，以 thread_id 标识；Checkpoint 是某个执行步骤保存的 State Snapshot，包含状态值、下一节点、任务和元数据等。

调用持久化图时必须提供稳定的 thread_id。复用同一 ID 会继续同一会话；新 ID 会创建新状态。生产系统还需校验该 Thread 是否属于当前用户/租户。

执行快照与跨会话数据

Checkpointer 保存单个 Thread 的 Graph State，用于短期记忆、恢复、HITL、Time Travel 和容错；Store 保存应用定义的跨 Thread 数据，用于长期偏好、事实或共享知识。

例如“当前会话已经调用过哪些工具”属于 Checkpoint State；“这个用户偏好中文回答”可以存 Store。长期事实仍应有来源、更新时间、权限和删除机制。

短期记忆、长期事实与数据生命周期

Short-term Memory 通常是 Thread State 中的消息和自定义字段，由 Checkpointer 持久化；Long-term Memory 写入 Store，并按 User/Namespace 跨 Thread 检索。

Memory 不是越多越好。写入前应判断信息是否值得长期保存、是否得到授权、是否包含敏感信息，并设置作用域、过期和删除策略。

完整历史与模型可见上下文

Checkpoint 可以保存完整历史，但模型每次不应读取全部历史。常用策略包括：

  • 按 Token Trim，只保留最近消息；
  • 删除低价值 Tool Result；
  • 将早期对话总结为结构化摘要；
  • 抽取长期事实到 Store；
  • 对历史做检索式 Memory。

摘要会丢信息且可能产生错误，因此原始审计记录、模型可见上下文和长期记忆最好分层保存。

人工介入与故障恢复

人工介入的暂停与恢复协议

Node 调用 interrupt(payload) 后，LangGraph 通过 Checkpointer 保存当前状态并把可序列化 Payload 返回给调用方。用户审批或补充信息后，应用用相同 thread_id 和 Command(resume=value) 重新调用，Resume Value 成为 interrupt() 的返回值。

前置条件是 Durable Checkpointer 和稳定 Thread ID。审批 Payload 还应包含动作摘要、目标资源和参数，而不是只显示“是否同意”。

恢复时的节点重放与副作用

恢复 Interrupt 时，包含 interrupt() 的 Node 会从头重新执行，因此 Interrupt 前的代码也会再次运行。如果那里已经发送邮件、扣款或写数据库，就可能重复产生副作用。

应把副作用移到审批之后，或封装成可持久化 Task 并使用幂等键/唯一约束。不要依赖 Node 的局部变量在暂停后仍存在。

持久执行依赖幂等边界

Durable Execution 让流程在进程重启、失败或人工暂停后从已保存进度继续，而不是从头计算。为了恢复时得到一致轨迹，非确定性调用和副作用要位于可持久化的 Task/Node 边界。

某个已开始但尚未确认完成的任务可能在恢复时再次执行，所以数据库写入、支付、发信等必须使用 Idempotency Key、状态检查或事务性 Outbox。

并行步骤中的 Pending Writes

同一 Super-step 中若一个并行节点失败，其他已成功节点的写入可以作为 Pending Writes 保存。恢复时无需重新执行这些成功节点，只重试失败部分，从而减少重复模型/API 调用。

这仍不替代外部副作用幂等性：运行时知道 State Write 成功，不一定知道外部系统是否已处理请求。

历史回放、分叉与状态更新

Replay 从旧 Checkpoint 重新执行其后的节点；Fork 基于旧 Checkpoint 修改状态并产生一条新轨迹；update_state 创建带更新值的新 Checkpoint，而不是修改历史快照本身。

旧 Checkpoint 之前的节点结果通常被复用，之后的 LLM、API 和 Interrupt 会重新执行，结果可能不同。Time Travel 适合调试和人工纠错，但涉及外部副作用时必须隔离测试环境或使用幂等控制。

子图中的状态边界

子图的封装与持久化模式

Subgraph 用于封装可复用流程、划分团队边界或构建 Specialist/Multi-agent。本文所依据的文档中的主要 Checkpointer 模式包括：

  • None：默认按单次调用使用，并继承父图能力，适合一次性子任务；
  • True：子图按 Thread 保持自己的状态，适合需要多轮记忆的子 Agent；
  • False：无持久化，不能使用 Interrupt/Durable Execution。

不应默认让所有子 Agent 都跨轮记忆，否则容易出现状态污染、命名空间冲突和难以解释的行为。

交付、观测与安全

流式事件与前端状态

当前主要模式包括：

  • updates：每一步的增量 State Update；
  • values：每一步后的完整 State；
  • messages：LLM Token/Message Chunk 及元数据；
  • custom：Node/Tool 主动发送的业务进度；
  • checkpoints：Checkpoint 事件；
  • tasks：任务开始、结束、结果和错误；
  • debug：更完整的调试事件。

其中 checkpoints 和 tasks 需要 Checkpointer。前端通常组合 Token 流、工具状态和业务进度。不能把内部 Chain-of-Thought 原样流给用户；应流式输出可公开的状态摘要。

异步、并发与流式交付的区别

异步让线程等待 I/O 时处理其他任务；并发表示多个任务的执行时间重叠；Streaming 表示结果逐步交付。三者可以组合，但互不等价。

生产中还需设置 Semaphore、连接池、供应商 Rate Limit、队列和客户端 Backpressure。客户端断开后是否取消模型/工具调用，也应有明确策略，否则会继续消耗资源。

错误分类与局部恢复

先分类：临时网络/限流错误可退避重试；Schema/参数错误可反馈给模型有限次修正；权限和业务规则错误不应重试；未知系统错误进入失败状态或人工处理。

应在最小安全边界重试，为每个 Node/Tool 设置 Timeout，并保留原始错误分类和 Trace。Fallback 只能切换能力兼容的模型或工具；恢复工作流时还要考虑副作用是否已经发生。

从执行轨迹到分层评估

Trace 应记录一次请求中的模型调用、Prompt 版本、Tool Call、Tool Result、Node 路径、Token、延迟、错误和关键 Metadata。敏感信息需要脱敏，Tenant 信息要用于访问控制而不是公开标签。

评估不能只看最终回答。至少拆成：

  • Task Success/答案正确性；
  • Tool Selection 与参数正确性；
  • Trajectory 是否合理、是否存在多余步骤；
  • RAG Recall、引用和 Groundedness；
  • 结构化输出通过率；
  • HITL 触发是否正确；
  • p50/p95 延迟、Token、成本和失败率；
  • Prompt Injection、越权和副作用安全。

离线 Golden Dataset 用于回归，线上 Trace/用户反馈用于发现新失败切片；LLM-as-Judge 需要用人工样本校准，不能作为唯一真值。

对检索、工具与状态设置安全边界

主要风险包括检索文档中的 Prompt Injection、模型越权选择工具、Tool 参数注入、跨租户状态/缓存泄漏、敏感信息进入 Trace、危险写操作重试，以及 SSRF/SQL/路径遍历等传统漏洞。

防护原则是：模型输出始终不可信；工具使用 Allowlist 和严格 Schema；执行层重新鉴权；读写工具分级；高风险动作审批；缓存键包含权限作用域；文档指令与系统指令分隔；输出到 SQL、Shell、URL 时继续做确定性校验。

验证实现的执行约定

实现完成后，可以逐项核对以下执行约定：

  1. State 有哪些字段，哪些字段使用 Reducer，为什么；
  2. Thread ID 怎样生成并与用户/会话绑定；
  3. Checkpointer 使用什么存储，进程重启后能否恢复；
  4. Interrupt 恢复时哪些代码会重跑，副作用如何幂等；
  5. Tool 的 Schema、权限、Timeout 和错误怎样设计；
  6. 并行分支如何合并，是否遇到 State Update 冲突；
  7. Streaming 给前端哪些事件，断线如何处理；
  8. 如何限制循环、Token、成本和并发；
  9. Trace 中怎样定位一次错误 Tool Call；
  10. 上线前用什么数据集和指标做回归。

故障定位应保留具体证据：输入是什么、Trace 显示哪一步错了、根因在 Prompt/Tool/State/Reducer/权限还是模型、如何修复，以及用什么回归用例防止复发。

下面几组边界决定了恢复和权限设计：

Tool Call ≠ Tool Execution
State ≠ Runtime Context ≠ Store
Checkpointer ≠ Long-term Store
Interrupt Resume ≠ 从断点下一行继续
可计算/可重试 ≠ 副作用可安全重放
