工具调用：模型意图、执行权限与系统评估

拆解工具请求的校验与执行边界，说明最小权限、幂等和失败处理，并建立覆盖任务、证据、安全和效率的应用评估。

W韦君豪约 5 分钟

工具调用让语言模型能够访问实时信息和执行具体动作，也把应用带到了真正的权限边界前。模型生成工具名和参数，服务端决定动作是否允许、能否重试以及怎样处理失败。只有把这些职责分开，任务灵活性才不会变成不可控的副作用。

查看图示的文字结构
flowchart TD
    M["模型生成工具名与参数"] --> S["Schema 与业务语义校验"]
    S --> A["身份、租户、资源与权限校验"]
    A --> B["审批、预算、超时与幂等检查"]
    B --> T["服务端执行工具"]
    T --> R["结构化结果与证据"]
    R --> M
    T --> F["分类记录错误与副作用状态"]
    F --> D{"是否可安全重试"}
    D -->|"是"| B
    D -->|"否"| H["停止、降级或人工处理"]

循环表示模型可以继续决策，但每一次执行都重新经过校验。错误处理先判断权限、参数与副作用状态，不能把所有失败统一当作可重试的网络问题。

从调用意图到真实执行

Function Calling 让模型输出符合工具 Schema 的调用意图，由应用执行真实 API，再把结构化结果返回模型。模型因此可以访问实时数据、执行计算或触发业务动作，但工具权限和副作用仍由服务端控制。

完整执行链

用户问题
→ 模型选择工具并生成参数
→ Schema 校验
→ 身份、租户、权限和审批
→ 超时、预算与幂等检查
→ 服务端执行工具
→ 结构化 tool result
→ 模型继续规划或生成答案
→ 保存工具轨迹与证据

为什么不只是“生成 JSON”

  • Schema 只能检查形状，业务合法性还要服务端验证；
  • 模型给出的 user_id/project_id 不能作为权限依据；
  • 有副作用的工具需要确认、幂等键和补偿；
  • 只读工具也要限制租户、结果大小和敏感字段；
  • Tool result 可能包含 Prompt Injection，需要按不可信数据处理；
  • Agent 还需要 step limit、调用预算、取消和错误恢复。

工程应用

可以用静态业务工具、严格的参数 Schema、具有作用域的 Tool Context 和 Human-in-the-loop 审批组织执行；引用和业务卡片则由成功工具结果派生。这样能把工具调用与可验证的产品输出联系起来。

把权限放在确定性的执行边界

核心原则是最小权限：敏感数据不进入公开训练语料，推理时先由服务端按用户、项目和数据源过滤，再把最小必要上下文交给模型。RAG 只是数据入口，还需要 ACL、工具权限、Prompt Injection 防护、输出检查和日志治理。

分层措施

  1. 训练与模型层

    • 训练数据分类、去密和授权检查；
    • Canary 与记忆提取评测；
    • 机密知识优先留在受控数据源，不固化进通用权重。

  2. 检索层

    • 检索前执行 tenant/user/document ACL；
    • Cache key 包含权限范围和数据版本；
    • 返回最小必要 Chunk，并去除密钥、凭据和敏感字段。

  3. Agent/Tool 层

    • 工具由服务端静态注册并按用户过滤；
    • 高风险读取或副作用需要审批；
    • 限制任意 URL、Shell、SQL 和网络出口；
    • 将网页、附件和工具结果视为不可信数据，防止间接 Prompt Injection。

  4. 输出与运维层

    • DLP/PII 检查与必要脱敏；
    • 日志中避免保存原始凭据和完整敏感 Prompt；
    • 记录访问主体、数据源、工具和决策；
    • 定期执行数据外泄和越权红队测试。

工程应用

项目角色权限、品牌共享范围、数据源许可和工具审批可以分层实现，使模型决策与业务权限保持解耦。

按任务、证据、安全与系统分层评估

评估应从模型分数扩展到任务、证据、安全和系统四层。离线黄金集回答“能力如何”，在线指标回答“真实用户是否完成任务”，二者都要按场景切片并跟踪回归。

评估矩阵

维度 示例指标
Task Quality Exact Match、F1、任务成功率、人工偏好
Helpfulness 完整度、可执行性、用户解决率
Factuality 事实正确率、claim verification
Groundedness 上下文支持率、citation precision/recall
Retrieval Recall@k、MRR、NDCG、无结果率
Robustness 拼写扰动、Prompt 改写、长上下文、OOD
Safety Toxicity、越权、隐私、Jailbreak、误拒率
Agent 工具选择准确率、参数正确率、步骤数、恢复率
Efficiency TTFT、TPOT、p95 延迟、Token、成本、吞吐
Operations 错误率、重试率、缓存命中、回滚与漂移

LLM-as-a-Judge 的使用方式

LLM Judge 适合开放式回答的规模化初筛，但要：

  • 明确 rubric，并让 Judge 分维度打分；
  • 随机交换候选顺序，测位置偏差；
  • 隐藏模型身份，避免风格偏好；
  • 用人工标注集校准 Judge 一致性；
  • 对关键安全与事实问题使用规则、工具或人工复核；
  • 记录 Judge 模型和 Prompt 版本。

评测流程

定义真实任务和失败成本
→ 建立黄金集与困难切片
→ 对各模块分别测量
→ 端到端回放
→ 人工复核高风险样本
→ 灰度/A-B 测试
→ 监控漂移并把失败样本回流

工程应用

视觉审核可以按角色识别、规则规划、边界框、素材召回、几何验证和最终发现分层评估；Agent 可以按工具选择、权限、证据支持、任务成功率、Token 和延迟评估。
