LLM inference: KV caches, continuous batching, and serving performance

Inference optimization is not a single generation-speed number.

WJunhao WeiAbout 4 min read

Inference optimization is not a single generation-speed number. Prefill for long inputs, cache access during decoding, and scheduling across shared devices jointly affect latency, throughput, and memory. Separate those costs before deciding which bottleneck caching, quantization, batching, or parallelism addresses.

Continuous batching changes active requests between decoding iterations instead of waiting for a fixed batch to finish. Prefill and decoding still compete for resources; greater throughput does not automatically lower first-token or tail latency.

KV caching removes repeated computation over past tokens

When generating token ttt, the keys and values of the previous t−1t-1t−1 tokens remain unchanged at each layer. Cache those tensors, compute only the new token’s Q/K/V, and attend to the accumulated keys and values rather than rerunning the whole prefix.

Computation and memory

Without caching, every step recomputes a growing full sequence. Caching avoids repeated historical projections and earlier-layer computation. At step ttt, the new query still interacts with ttt keys, giving approximately O(t)O(t)O(t) attention per step and O(T2)O(T^2)O(T2) across generation. KV caching eliminates repeated forward work, not all quadratic attention interactions.

A rough KV-memory estimate is:

MKV=2×L×T×Hkv×dhead×b×BM_{KV}=2\times L\times T\times H_{kv}\times d_{head}\times b\times BMKV​=2×L×T×Hkv​×dhead​×b×B

The factor 2 accounts for K and V; LLL is layer count, TTT cached length, HkvH_{kv}Hkv​ KV-head count, bbb bytes per element, and BBB the number of concurrent sequences.

Optimization options

  • MQA/GQA: Share fewer KV heads across query heads.
  • KV quantization: Reduce cache precision with formats such as FP8/INT8.
  • Paged KV cache: Allocate pages to reduce reservation waste and fragmentation.
  • Sliding-window/chunked attention: Limit the effective history.
  • Prefix caching: Reuse identical prompt prefixes across requests.
  • KV offload: Move cache to CPU or another tier, trading memory for transfer costs.

Evaluate latency, throughput, and cost together

Report latency, throughput, concurrency, memory, and unit cost, distinguishing prefill from decoding. A bare “tokens/s” is insufficient: specify whether it measures one request or an entire device, along with input/output lengths, batching, and percentiles.

Core metrics

Metric Meaning Main influences
TTFT Request arrival to first output token Queue, prompt length, prefill, scheduling
TPOT / ITL Average time between output tokens Decoding, KV bandwidth, batch, communication
End-to-end latency Time for the complete response TTFT + output length × TPOT
Request throughput Completed requests per second Length distribution, batching, scheduling
Token throughput Total generated tokens per second GPU utilization, parallelism, kernels
Concurrency Active sequences served together KV cache, memory, scheduling
Cost per request GPU time or monetary cost Model, length, caching, utilization

Token efficiency can also describe input/output tokens per successful task, cache hits, retries, and cost per successful outcome.

Typical trade-offs

  • Larger batches often increase aggregate throughput but may increase queues and individual latency.
  • Tensor parallelism accommodates larger models but adds inter-device communication.
  • Longer context increases prefill and KV storage.
  • Quantization saves memory and bandwidth, subject to quality and kernel support.
  • Speculative decoding spends extra draft computation to reduce target-model decoding iterations.

Continuous batching and scheduling

Static batching keeps requests together, often retaining resources until the whole batch completes. Short outputs can be held back by long ones. Continuous batching removes completed sequences after each decoding iteration and fills free slots with new requests, improving GPU and cache utilization.

Execution flow

等待队列
  → Scheduler 选择可进入的 Prefill/Decode 请求
  → 执行一个或若干 iteration
  → 回收已结束请求的 KV block
  → 加入新请求
  → 下一 iteration

Continuous batching often works with PagedAttention or paged KV caches: memory is allocated dynamically in blocks rather than reserving the maximum contiguous region per sequence. This reduces internal fragmentation and supports flexible swapping.

Scheduling challenges

  • Long-prompt prefill can block decoding and cause TPOT variation.
  • TTFT and smooth ongoing decoding may require different priorities.
  • Lengths and sampling settings change batch shapes.
  • Prefix caches, LoRA adapters, and tenant priorities add constraints.
  • High throughput does not guarantee low tail latency; inspect p95/p99.
