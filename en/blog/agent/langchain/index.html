LangChain: Building LLM Applications with Clear Component Boundaries

Not every application needs an agent that plans its own actions.

WJunhao WeiAbout 9 min read

Not every application needs an agent that plans its own actions. Single calls, fixed retrieval pipelines, and model-driven tool loops differ in complexity and failure modes. LangChain offers reusable model, message, tool, and retrieval components; abstraction choices should follow state complexity, recovery needs, and maintenance cost.

Component reuse, model decisions, and durable execution address different needs. Fixed workflows can reuse the same components, while complex state management requires an additional runtime protocol, not merely another model call.

This article follows official Python documentation from August 2026. Check the language, package, and version when applying APIs that continue to evolve.

Identify the problem the abstraction solves

Components versus a stateful runtime

LangChain supplies high-level models, messages, tools, retrievers, prompts, middleware, structured output, and agents. LangGraph supplies lower-level state/node/edge orchestration for loops, branches, persistence, pause/resume, long workflows, and human intervention.

LangChain's create_agent runs on LangGraph. They are complementary: use LangChain components and explicit LangGraph orchestration where needed. A single prompt–model–parser call rarely needs a graph; approvals, recovery, validation loops, and deterministic stages make it more useful.

Costs and benefits of stateful orchestration

Python already supports loops and branches. LangGraph's value is a shared protocol for state updates, concurrent merging, checkpoints, thread recovery, interrupts, streaming, and observable execution—not simply drawing a graph.

Short workflows without recovery needs may be simpler in ordinary code. Tasks lasting minutes or hours, human approvals, recovery midway, historical inspection, and parallel nodes can justify avoiding custom runtime infrastructure.

When to keep the implementation simple

A framework may be unnecessary when a few fixed functions suffice, latency is extremely tight, the business flow must remain deterministic, only a small part of a provider SDK is needed, or abstraction hides important provider features and errors. Choose based on complexity, replaceability, recovery, and observability rather than résumé keywords.

How workflows and agents execute

Fixed paths and runtime action selection

A chain's path is largely developer-defined; an agent lets the model decide which tool to call, whether another action is needed, and when to finish. Chains offer more predictable tests, latency, and costs. Agents suit variable intent and step counts. Production systems often combine a deterministic outer workflow with local agent decisions.

One LLM call alone does not make an agent. Model-driven action selection or iterative decisions are the distinguishing behavior.

The model–tool–observation loop

The model receives messages and tools, then returns a final answer or tool call. The runtime validates and executes calls, appends results, and asks the model to decide again until completion or a stop condition.

Production limits must cover steps, tokens, elapsed time, parallel tools, and side-effect permissions to prevent runaway loops and costs.

Composition, concurrency, and delivery

Compose work with Runnables

LCEL connects executable components using operators such as |. Its Runnable abstraction supports invocation, batching, streaming, asynchronous execution, and further composition.

chain = prompt | model | parser

RunnableSequence passes outputs serially; RunnableParallel runs independent branches on one input. Clear dataflow suits LCEL, while complex loops, stateful branches, and recovery usually favor LangGraph.

Synchronous, asynchronous, batch, and streaming interfaces

invoke handles one input synchronously; ainvoke handles it asynchronously, useful for I/O. batch/abatch handle independent inputs, potentially using thread pools, asyncio.gather, or integration-specific native batching. stream/astream deliver incremental output to improve perceived latency, not necessarily total computation.

Add timeouts, cancellation, concurrency limits, backpressure, and error aggregation. Async alone does not guarantee higher throughput.

Sequential dependencies and parallel branches

Dependent steps must remain ordered: retrieve before answering. Independent work, such as summary and keyword extraction, can run concurrently. Parallelism raises instantaneous QPS, rate-limit exposure, result-merging complexity, and partial-failure handling. Shared external writes also need concurrency safety.

Retry at the smallest safe boundary

Retry transient model/API failures where replay is safe, rather than rerunning an entire agent. Fallback switches unavailable models, retrievers, or providers to alternatives.

Non-idempotent writes cannot be retried blindly. Permanent argument or permission errors should not enter exponential backoff. Fallbacks may differ in tool support, context limits, or structured output. Retries increase tail latency and cost, requiring budgets and circuit breakers.

Prompts, messages, and context

Roles and data boundaries in templates

PromptTemplate produces strings; ChatPromptTemplate produces role-aware System/Human/AI/Tool messages. Boundaries affect instruction priority, prompt caching, and tool calling. Template values remain untrusted: place user content in explicit data positions instead of concatenating it into apparent system instructions.

Preserve message structure and call relationships

Messages include roles, tool calls and IDs, structured content blocks, response metadata, and token usage. Agent loops require correct pairing of AIMessage.tool_calls with ToolMessage.tool_call_id. Flattening history into text loses roles, call relationships, multimodal structure, and normalized provider semantics.

State, runtime context, and store

State contains mutable workflow/thread data such as messages and intermediate results. Runtime context injects dependencies, user identity, or database connections without making them graph state. A store holds application-defined cross-thread preferences, memories, or facts.

Connections in state cause serialization problems; secrets in checkpoints leak sensitive data; copying a business database into a store creates consistency and double-write problems.

Tools and runtime extensions

Tool responsibilities, inputs, and returns

A good tool has one clear purpose, a stable name, accurate description, strict schema, predictable return structure, and observable errors. Models select tools largely from these descriptions and schemas.

Validate enums, ranges, and business IDs. Recheck authentication and authorization inside execution. Bound timeout, retries, and result size. Use idempotency keys, approvals, or dry runs for writes. Return stable error types rather than raw stack traces.

Separate requested actions from execution authority

Tool calling is a structured request containing a name and arguments. Execution belongs to the application after validation. Check the user, tenant, resource IDs, approval state, and parameters at that boundary. Omitting a field from the model's schema does not itself prevent unauthorized access.

Centralize cross-cutting behavior with middleware

Hooks around model calls and tools support dynamic prompts/models/tools, logs, retries, fallback, rate limits, PII detection, guardrails, summaries, and human intervention. Middleware suits cross-cutting logic but should not conceal essential business state transitions. Document order and test each layer; too many hooks obscure error propagation.

Select tools by permission and workflow stage

Static tools are fixed at agent creation and easy to test. Dynamic selection filters by permissions, task stage, context, or model capability, reducing choices and exposure. Hidden tools still require authorization at execution. Frequently changing tool sets can also affect prompt caches and behavioral stability.

Structured results and retrieval

Provider constraints and tool-based output

ProviderStrategy uses native structured-output constraints; ToolStrategy uses tool calls where native support is unavailable. create_agent(response_format=Schema) selects according to model capability. Both require handling validation errors, multiple structured outputs, retry limits, and business meaning. Schema-valid fields can still be wrong.

Business validation after syntax constraints

Prefer native structured output where available, then tool calling, with free-text JSON/regex parsing as the more fragile option. Markdown, explanations, and truncation break free-text parsers. No syntax strategy establishes that dates are real, IDs exist, or amounts fit business limits; deterministic checks remain necessary.

Offline and online retrieval paths

An offline pipeline loads, cleans/parses, splits, embeds, and indexes documents. Online work interprets queries, retrieves or hybrid-searches, reranks/compresses, constructs context, generates, and verifies citations. Modular components ease replacement but do not guarantee RAG quality. Evaluate recall, ranking, context use, and groundedness separately.

Retrievers and vector stores

A vector store persists and searches vectors. A retriever is the broader query-to-documents interface and can wrap vector search, BM25, enterprise/web search, databases, or combinations. Using a retriever implies neither a vector database nor similarity-only retrieval.

Fixed retrieval, agentic RAG, and hybrid flows

Two-step RAG retrieves then generates with predictable behavior. Agentic RAG lets the model choose timing, sources, rewriting, and repeated searches. Hybrid RAG combines deterministic requirements—such as permission filtering and baseline recall—with optional agent exploration.

Evidence-dependent, high-risk tasks should not rely solely on the model deciding to retrieve. Require appropriate retrieval or database checks and decline unsupported answers.

Choose chunks by structure and evaluation

Chunks must be precise enough for retrieval and large enough to retain meaning. Overlap reduces boundary loss but expands indexes, duplicate results, and context tokens. Split code by functions/classes, Markdown by headings, contracts by clauses, and tables with their headers intact. For general text, RecursiveCharacterTextSplitter is a starting point; tune using answer-bearing chunk recall, answer quality, and cost.

Let execution needs determine the architecture

Explicit retrieval, validation, approval, execution, and persistence stages—especially approvals spanning requests and recovery midway—can benefit from LangGraph state transitions with LangChain components.

For a mainly model–tool loop, a thinner runtime may better match SDK streaming, frontend integration, and maintenance needs. Drawing a workflow graph is different from implementing durable execution, interrupts, and complex branching. Compare actual capabilities rather than inferring identical recovery semantics from similar concepts.
