Tool calling: separate model intent from execution authority

Tool calling gives language models access to current information and concrete actions, bringing an application to a real authorization boundary.

WJunhao WeiAbout 5 min read

Tool calling gives language models access to current information and concrete actions, bringing an application to a real authorization boundary. The model proposes a tool and arguments; the server decides whether the action is allowed, whether it can be retried, and how failure is handled. Separating these responsibilities prevents flexibility from turning into uncontrolled side effects.

The loop allows further model decisions, but every execution passes validation again. Error handling first checks permissions, arguments, and the state of side effects. Not every failure is a retryable network error.

From intent to actual execution

Function calling asks a model to express an intended call using a tool schema. The application executes the real API and returns a structured result. This enables live data access, calculation, and business actions, while the server retains control over permissions and side effects.

Why this is more than generating JSON

  • A schema checks shape; the server must still validate business rules.
  • Model-supplied user_id or project_id is not proof of authorization.
  • Side-effecting tools need approval where appropriate, idempotency keys, and compensation.
  • Read-only tools still need tenant scoping, result-size limits, and sensitive-field controls.
  • Tool results may contain prompt injection and must be treated as untrusted data.
  • Agents also need step limits, call budgets, cancellation, and recovery.

Engineering application

Execution can combine statically registered business tools, strict argument schemas, scoped tool context, and human approval. Derive citations and business cards from successful tool results to connect actions to verifiable product outputs.

Enforce permissions at a deterministic execution boundary

Apply least privilege. Keep sensitive data out of public training corpora, filter inference-time access on the server by user, project, and source, and give the model only the necessary context. RAG is merely an entry point; ACLs, tool authorization, prompt-injection defenses, output checks, and log governance remain necessary.

Layered measures

  1. Training and models: Classify and de-identify training data, check authorization, evaluate canaries and memorization extraction, and keep confidential knowledge in controlled sources rather than general-purpose weights.
  2. Retrieval: Apply tenant, user, and document ACLs before retrieval. Include permission scope and data version in cache keys. Return only necessary chunks, removing credentials and sensitive fields.
  3. Agents and tools: Register tools statically on the server and filter them by user. Require approval for high-risk reads or side effects where appropriate. Restrict arbitrary URLs, shell commands, SQL, and network egress. Treat pages, attachments, and results as untrusted to prevent indirect prompt injection.
  4. Outputs and operations: Apply DLP/PII checks and redaction. Avoid raw credentials and full sensitive prompts in logs. Record the access principal, sources, tools, and decisions. Regularly red-team exfiltration and unauthorized access.

Engineering application

Project roles, brand-sharing scope, source licenses, and tool approvals can be implemented in separate layers, keeping model decisions independent of business authorization.

Evaluate tasks, evidence, safety, and systems separately

Extend evaluation beyond model scores to task outcomes, evidence, safety, and system behavior. Offline reference sets test capability; online metrics test whether users actually complete tasks. Slice both by scenario and track regressions.

Using an LLM judge

An LLM judge can screen open-ended answers at scale, provided that you:

  • Define a rubric and score dimensions separately.
  • Randomize candidate order to measure position bias.
  • Hide model identities to reduce style preferences.
  • Calibrate agreement against human labels.
  • Use rules, tools, or human review for critical safety and factual questions.
  • Record judge model and prompt versions.

Engineering application

A visual review system can be evaluated at character identification, rule planning, bounding boxes, asset retrieval, geometric verification, and final findings. An agent can be assessed through tool choice, authorization, evidence support, task success, token use, and latency.
