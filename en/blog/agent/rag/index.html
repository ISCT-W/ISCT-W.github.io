RAG: turn retrieved material into answers that can be checked

RAG lets a model use external knowledge that can be updated, but information can still be distorted at every stage between ingestion and delivery.

WJunhao WeiAbout 7 min read

RAG lets a model use external knowledge that can be updated, but information can still be distorted at every stage between ingestion and delivery. Reliability requires more than retrieval recall or a link attached to an answer. Design sources, context organization, generation constraints, and citation verification separately, then trace failures to the stage responsible.

Retrieval is one part of the evidence chain. The checkpoints constrain accessible data, evidence admitted to context, and whether sources support the final claims. Results that do not contain an answer must not be presented as a confident conclusion.

Where hallucinations come from

An LLM predicts the next token in a conditional distribution; it does not query an invariably correct fact database. Missing knowledge, ambiguous prompts, conflicting training data, poor use of long context, and decoding choices can all produce fluent unsupported answers. Mitigation must address sources, constraints, verification, and abstention—not temperature alone.

Types of causes

  1. Model knowledge: The fact is absent, outdated, or inconsistent across sources.
  2. Input: A false premise, unclear reference, or request beyond available context.
  3. Generation objective: Pressure to answer without a learned stopping behavior when evidence is insufficient.
  4. Context use: Evidence is too long, badly positioned, contradictory, or buried in irrelevant text.
  5. Decoding: Greater randomness increases variation, but greedy or low-temperature decoding can also reproduce falsehoods consistently.
  6. Tools and data: Search, OCR, a database, or an API may already have returned an incorrect result.

Mitigations

  • Supply updatable knowledge through RAG, databases, or business tools.
  • Restrict candidate entities to a closed set and use structured identifiers.
  • Attach citations to claims and verify that the evidence supports them.
  • Use deterministic tools for numbers, dates, calculations, and permission-sensitive facts.
  • Constrain output structure through schemas or constrained decoding.
  • Add a verifier, self-consistency checks, or a second model’s review.
  • Define an explicit unknown outcome for insufficient evidence or tool failure.
  • Evaluate retrieval and generation separately.

Lower temperature mainly reduces randomness. Chain-of-thought prompting may assist multistep reasoning, but neither guarantees factuality.

Engineering application

One possible design derives citations from successful tool results, restricts character or asset candidates, and uses rule databases and geometric verification. High-risk facts then move from unconstrained text generation into a deterministic evidence protocol.

Failure paths from retrieval to citation

RAG adds external context to generation, but both retrieval and generation can fail. Missing the right document, separating conditions from conclusions during chunking, incorrect reranking, conflicting context, ignored evidence, and forced answers can all cause hallucinations.

Failure chain

Stage Typical failure Diagnostic metric
Ingestion OCR errors, lost table structure, stale versions Document coverage, parsing accuracy
Chunking Split conditions and conclusions; inappropriate chunk size Retrievability of answer-bearing chunks
Retrieval Query mismatch, semantic drift, no results after permission filtering Recall@k, MRR, empty-result rate
Rerank Relevant documents demoted NDCG, top-k hits
Context Excess length, conflict, lost-in-the-middle Context precision, positional ablations
Generation Parametric memory overrides evidence; incorrect attribution Faithfulness, groundedness
Citation A citation exists but does not support the claim Citation precision and recall

Improvements

  • Query rewriting, multiple queries, metadata filters, and hybrid retrieval.
  • Parent–child, sentence-window, or structure-aware chunking.
  • Cross-encoder or LLM reranking.
  • Checking that context contains an answer before generation.
  • Claim-level citations with entailment checks.
  • Showing sources and dates when evidence conflicts, rather than forcing agreement.
  • Clarification, another tool, or abstention when retrieval is empty.
  • Treating pages and documents as untrusted inputs and handling prompt injection.

Organize RAG as a maintainable system

Enterprise RAG combines data, retrieval, generation, permissions, evaluation, and operations. Its core flow is:

数据接入与版本
→ 解析/OCR/清洗
→ 结构感知分块
→ Embedding + 关键词/结构化索引
→ 权限与元数据过滤
→ Query 理解/改写
→ Hybrid Retrieval
→ Rerank 与上下文压缩
→ 生成、引用与拒答
→ 评估、反馈和可观测性

Responsibilities by layer

Data

  • Retain document owner, tenant, version, effective date, and permissions.
  • Parse PDFs, tables, images, and code using suitable strategies.
  • Deduplicate while preserving parent–child structure, sections, and page numbers.
  • Update or remove index entries when documents change or are deleted.

Index

  • Dense embeddings capture semantic similarity.
  • BM25 and keywords cover names, identifiers, and exact phrases.
  • Structured fields support metadata filtering.
  • Choose HNSW, IVF, or a managed vector store for the data scale.
  • Version the index when upgrading the embedding model.

Retrieval

  • Identify the question type and time range.
  • Rewrite or decompose queries, or perform multi-hop retrieval.
  • Fuse hybrid retrieval scores.
  • Rerank with a cross-encoder or LLM.
  • Deduplicate, compress context, and enforce a token budget.

Generation

  • Specify which context must ground the answer.
  • Bind each claim to a source.
  • Clarify or return unknown when evidence is missing.
  • Assign distinct trust levels to tool results and document text.
  • Produce structured outputs when downstream code needs them.

Platform

  • Enforce tenant isolation and document-level ACLs.
  • Include user, project, and permission scope in cache keys.
  • Record queries, retrieval, reranking, citations, tokens, latency, and errors.
  • Improve with both offline reference sets and online feedback.
  • Redact sensitive fields, maintain audit logs, and define retention policies.

Evidence quality versus model size

Once the right evidence is retrieved, generation may mostly involve extraction, summarization, rewriting, or structured output. A small model can sometimes do this with lower latency and cost. “Smaller models follow instructions better and hallucinate less” is not a general rule: results depend on context length, task difficulty, language, instruction following, and training data.

Suitable uses for small language models

  • Fixed-schema extraction and classification.
  • Short-context, single-document question answering.
  • High-concurrency, low-latency internal assistants.
  • Edge deployment or local inference over sensitive data.
  • Task-specific optimization through distillation.
  • Systems where a router sends complex questions to stronger models.

Cases that may still need larger models

  • Resolving conflicts and reasoning across documents.
  • Multi-hop retrieval, complex planning, and tool coordination.
  • Fine-grained evidence integration in long contexts.
  • Low-resource languages or specialized domains.
  • High-quality explanations and open-ended writing.

Evaluation

Compare more than per-question accuracy: include task success, citation correctness, abstention rate, TTFT/TPOT, per-request cost, peak concurrency, and the fraction escalated to a larger model.

Reasoning compute and the limits of factuality

Chain-of-thought prompting uses intermediate steps to provide more inference-time computation for arithmetic, symbolic reasoning, and planning, instead of requiring a direct jump to the conclusion. The costs are more output tokens, latency, and opportunities for error propagation. Generated explanations may not faithfully describe the model’s actual decision process.

A fuller view

  • Few-shot CoT supplies examples with derivations.
  • Zero-shot CoT uses prompts such as asking for stepwise reasoning.
  • Self-consistency samples multiple reasoning paths and votes on answers.
  • Reasoning models may use longer internal reasoning during training and inference.
  • Agent scratchpads may track plans and tool observations without exposing all internal reasoning to users.

Products generally provide concise, checkable explanations or calculation steps instead of raw hidden reasoning. Security also cannot depend on hiding CoT: sensitive information should not enter model-visible context unnecessarily, and prompts, tools, and data need independent access controls.

Costs and risks

  • More tokens and higher latency.
  • Incorrect intermediate steps anchoring later answers.
  • Plausible reasoning text that is not faithful.
  • Extra noise when CoT is forced onto simple questions.
  • Leakage if sensitive internal context is copied into visible explanations.
