LangGraph: State, Recovery, and Long-Running Execution

Long workflows must do more than choose the next function.

WJunhao WeiAbout 9 min read

Long workflows must do more than choose the next function. They preserve progress, merge parallel updates, wait for people, and determine which operations can safely repeat after failure. LangGraph organizes these behaviors through graph state and persistence. Execution snapshots, model context, and external side effects must remain distinct: resuming does not simply continue at the next line after a pause.

State and execution progress are persisted, not arbitrary local variables. An interrupt saves the information needed to pause; the relevant node runs again on resume, so side effects need safe replay boundaries.

This article follows official Python documentation from August 2026. Verify persistence modes and streaming interfaces against your version.

State and update protocols

The contract between state, nodes, and edges

State defines a shared snapshot and schema. Nodes read it and return changed fields, not necessarily the complete state. Edges select subsequent nodes. Store stable facts and control fields needed by the workflow, rather than temporary objects, connections, and duplicate large texts.

Compilation and runtime configuration

Compilation turns the builder into an executable graph, checks basic structure, and binds settings such as checkpointers, stores, and breakpoints. It neither trains a model nor compiles Python into machine code. Usually compile once at process startup and reuse, rather than rebuilding graphs and database connections per request.

Schema validation and overhead

TypedDict is lightweight, dataclasses support defaults, and Pydantic offers stronger runtime validation/conversion with added overhead. Choose according to validation and performance needs. Returned updates, external tool results, and old checkpoints still require business validation; annotations alone do not prevent invalid data.

Reducers define merge semantics

A reducer combines an existing field with an update. Without one, updates usually replace values. List-like fields may append, deduplicate, or update by ID. Prefer deterministic reducers and consider order dependence. Concurrent writes to one field without appropriate merge semantics can conflict or become unpredictable.

Message merging needs identity and deletion

List concatenation cannot replace messages by ID or correctly handle deletion. Message reducers deserialize inputs and support append, replacement, and RemoveMessage. These semantics matter for streaming calls, human history edits, and context compression.

Routing, parallelism, and termination

Routing edges versus Command

Conditional edges use separate routing functions. Command returns state updates and goto together when updates and routing are tightly coupled. Prefer edges for pure routing and avoid arbitrary jumps from every node, which conceal control flow.

Send and dynamic fan-out

Send creates downstream tasks dynamically, commonly for map–reduce. Bound fan-out, concurrency, per-task timeout, and aggregate size; unlimited user-controlled expansion can exhaust resources and budgets.

Parallel execution in super-steps

The Pregel-like runtime can run several active independent tasks in one super-step, merge their updates, and choose the next set. Two outgoing edges do not imply serial execution in source order. Parallel nodes must avoid undeclared dependencies and unsafe side effects.

Conflicting writes and deterministic joins

Different fields can update independently. Multiple writes to one field need a compatible reducer or can trigger an update error. Split fields, define a business-appropriate reducer, return ID-tagged results for a deterministic join node, or make the steps explicitly serial.

Bound loops with several budgets

Use graph step/recursion limits, tool-call limits, time/token/cost budgets, repeated tool-and-argument detection, no-progress detection, and explicit terminal/failure states. On exhaustion, return an understandable partial result or request human intervention rather than exposing an internal exception alone.

Execution history and memory

Threads, checkpoints, and persistence

A checkpointer saves and loads snapshots. A thread is an independent execution/conversation identified by thread_id. Checkpoints include state values, next nodes, tasks, and metadata. A stable ID continues an existing conversation; a new ID starts new state. Verify user/tenant ownership in production.

Execution snapshots versus cross-conversation data

Checkpointers store per-thread graph state for short-term memory, recovery, human intervention, time travel, and fault tolerance. Stores hold application-defined cross-thread preferences or facts. Tools already called belong in execution state; a language preference can live in a store. Long-term facts need sources, timestamps, access control, and deletion.

Memory lifecycle

Short-term memory typically comprises persisted thread messages and fields; long-term memory is retrieved from user/namespace-scoped stores. More memory is not always better. Check relevance, authorization, sensitivity, scope, expiry, and deletion before writing.

Full history versus model-visible context

Persisting history does not mean sending all of it to the model. Trim by token count, remove low-value tool results, summarize older exchanges, extract durable facts, or retrieve relevant history. Summaries can omit or invent details, so separate audit records, model context, and long-term memory.

Human intervention and recovery

Pause and resume protocols

interrupt(payload) saves the relevant state through a checkpointer and returns a serializable payload. After human input, reinvoke with the same thread_id and Command(resume=value); that value becomes the interrupt's return value. Use durable storage and stable IDs, and show an action summary, resources, and parameters in approval payloads rather than merely asking for agreement.

Node replay and side effects

The interrupted node restarts from its beginning, including code before interrupt(). Email, charges, or writes there can repeat. Move effects after approval or isolate them in persisted tasks with idempotency keys/unique constraints. Local variables are not preserved as a suspended stack frame.

Durable execution needs idempotent boundaries

Saved progress allows continuation after restart, failure, or pauses. Nondeterministic calls and effects need persisted task/node boundaries. A task started but not confirmed complete can run again; writes, payments, and messages require idempotency, status checks, or a transactional outbox.

Pending writes in parallel steps

If one parallel node fails, successful sibling writes can be saved as pending writes. Recovery can retry only failed work. This reduces repeated model/API calls but does not replace external idempotency: a recorded state write and an external request's completion are different facts.

Replay, forks, and state updates

Replay executes nodes after an old checkpoint. Fork changes state from an old checkpoint to create a new trajectory. update_state creates a new checkpoint instead of altering history. Earlier results are generally reused, while later model calls, APIs, and interrupts run again and may differ. Isolate external effects or make them idempotent during time-travel debugging.

State boundaries in subgraphs

Encapsulation and persistence modes

Subgraphs encapsulate reusable work or specialist agents. In the referenced documentation, None uses per-invocation state and inherits parent capabilities; True retains per-thread subgraph state; False disables persistence and associated interrupts/durable execution. Give cross-turn memory only where needed to avoid state contamination and namespace conflicts.

Delivery, observability, and security

Streaming events and frontend state

Modes include updates for deltas, values for full state, messages for LLM chunks and metadata, custom for business progress, checkpoints, tasks, and fuller debug events. Checkpoint and task modes require a checkpointer. Frontends often combine tokens, tool status, and progress. Stream public status summaries rather than internal chain-of-thought.

Async, concurrency, and streaming are different

Async permits other work while waiting for I/O; concurrency overlaps tasks; streaming delivers partial results. Combine them as needed, with semaphores, connection pools, provider limits, queues, and backpressure. Decide whether client disconnection cancels model/tool work to avoid unintended resource use.

Classify errors and recover locally

Retry transient network/rate failures with backoff. Permit bounded correction of schema/argument errors. Do not retry permission or business-rule failures. Unknown system faults enter failure or human-handling paths. Retry at the smallest safe boundary, set node/tool timeouts, preserve error types and traces, and use only capability-compatible fallbacks. Check whether effects already occurred before recovery.

From traces to layered evaluation

Trace model calls, prompt versions, tools and results, node paths, tokens, latency, errors, and useful metadata. Redact sensitive information; tenant IDs belong in access control, not public labels.

Evaluate task success, tool selection and arguments, unnecessary steps, RAG recall/citations/groundedness, structured-output validity, appropriate human escalation, p50/p95 latency, tokens, cost, failures, prompt injection, authorization, and effect safety. Golden datasets support regression; live traces and feedback reveal new cases. Calibrate LLM judges with human examples instead of treating them as sole ground truth.

Security boundaries for retrieval, tools, and state

Risks include document prompt injection, unauthorized tools, argument injection, cross-tenant state/cache leaks, sensitive traces, unsafe retries, SSRF, SQL injection, and path traversal. Treat model output as untrusted; use tool allowlists and strict schemas, reauthorize execution, separate read/write privileges, approve high-risk actions, scope cache keys by permission, separate document data from system instructions, and validate SQL/shell/URL inputs deterministically.

Verify the execution contract

Check these implementation details:

  1. State fields and the reason for each reducer.
  2. Thread-ID generation and user/session binding.
  3. Checkpoint storage and recovery after process restart.
  4. Code replayed after interrupts and effect idempotency.
  5. Tool schemas, permissions, timeouts, and errors.
  6. Parallel joins and conflicting updates.
  7. Frontend event types and disconnection behavior.
  8. Loop, token, cost, and concurrency limits.
  9. Traces that locate an incorrect tool call.
  10. Regression datasets and metrics before release.

Keep concrete debugging evidence: inputs, the failing trace step, whether the cause was prompt/tool/state/reducer/permission/model, the correction, and the regression case.

These boundaries guide recovery and authorization design:

Tool Call ≠ Tool Execution
State ≠ Runtime Context ≠ Store
Checkpointer ≠ Long-term Store
Interrupt Resume ≠ 从断点下一行继续
可计算/可重试 ≠ 副作用可安全重放
